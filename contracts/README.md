# cutchain `contracts/`

On-chain plumbing for **CUT** on **Robinhood Chain** (chain id 4663, Arbitrum-Nitro L2), launched
through the **Pons** launchpad. Two small, dependency-free Solidity contracts plus the off-chain tool
that produces the weekly payout tree.

```
contracts/
├── src/
│   ├── CutPool.sol                 immutable fee splitter (dev / clipper pool / team)
│   ├── MerkleDistributor.sol       weekly Merkle payouts to clippers
│   ├── interfaces/{IERC20,IWETH}.sol
│   └── libraries/SafeTransferLib.sol   tiny vendored safe-transfer helper (no OpenZeppelin)
├── script/Deploy.s.sol             Foundry deploy script (env-driven)
├── test/                           Foundry tests + mocks + fixtures generated by the Python tool
├── tooling/
│   ├── build_round.py              views.csv -> round_<n>.json (root, amounts, proofs)
│   └── views.example.csv
├── foundry.toml, remappings.txt, .env.example, .gitignore
├── deploy.md                       step-by-step deployment + weekly ops commands
└── README.md                       this file
```

## How money flows

```
 Uniswap V3 pool (CUT/WETH, 1% fee)
        │ 70% of fees accrue to the token creator inside the locked LP position (Pons V1 locker)
        ▼
 Pons locker ── claim ──► creator fee wallet
                              │
                              │  mode A: dev wallet forwards our share manually
                              │  mode B: the fee wallet IS CutPool, claim is permissionless
                              ▼
                          CutPool  ──distribute()──►  dev (x bps)
                                                       team (y bps)
                                                       MerkleDistributor (z bps)
                                                            │
                                            owner publishes weekly Merkle root
                                                            │
                                                            ▼
                                          clippers claim(roundId, index, account, amount, proof)
```

## Contracts

### `CutPool` — immutable fee splitter

- Constructor: `(address[] recipients, uint16[] bps, address claimTarget, bytes4 claimSelector)`.
  `bps` must sum to 10 000; every recipient and weight is fixed forever (no owner, no setters, no
  upgrade, no generic `execute`).
- `receive()` accepts ETH (and stays under WETH9's 2 300-gas `transfer` stipend).
- `distribute()` splits the whole ETH balance; `distributeToken(token)` splits any ERC-20 balance.
  Anyone can call them. Emits `Distributed(token, amount)` plus one `Paid` per recipient.
  Rounding: recipients `0..n-2` get `floor(amount * bps / 10000)`, the **last recipient gets the
  remainder**, so at most `n-1` wei of dust per distribution goes to the last recipient and nothing
  is ever stranded. `previewSplit(amount)` returns the exact shares.
- `unwrapWETH(weth)` calls `withdraw(balance)` on a WETH-like contract so WETH fees can be split
  as ETH. It checks that the ETH balance grew by exactly the unwrapped amount, so passing a
  non-WETH address cannot make the contract do anything useful for an attacker.
- `claim(bytes data)` — permissionless — performs one zero-value low-level call to `claimTarget`
  (the Pons locker) so anyone can trigger the creator-fee claim into CutPool when CutPool is the
  token's registered creator / fee wallet. Reverts if `claimTarget` is zero, and reverts unless
  `data` starts with `claimSelector`. This is the only outbound call the contract can make on
  someone's behalf.

  Why the selector lock (a deliberate addition to the brief): if CutPool is the token's creator and
  the locker exposes creator-only functions such as `setFeeRedirect(token, newWallet)`, an
  unrestricted `claim(bytes)` would let *anyone* redirect the fee stream to themselves. Pinning the
  selector at deploy time keeps `claim` permissionless while making it single-purpose. The trade-off
  is that the locker's claim signature must be known before CutPool is deployed (see *Known
  unknowns*); CutPool can still be deployed with `claimTarget = 0` for mode A.

### `MerkleDistributor` — weekly clipper payouts

- Single `owner` (two-step transfer: `transferOwnership` → `acceptOwnership`).
- `setRound(roundId, token, merkleRoot, total, claimDeadline)` — owner only, **once per roundId**.
  `token == address(0)` means ETH. Requires the contract to already hold `total` of that token *on
  top of* what every other open round still owes (`reserved[token]`), so a new round can never eat
  into an older round's funds.
- `claim(roundId, index, account, amount, proof)` — permissionless; tokens always go to `account`.
  Uniswap-style 256-bit claimed bitmap per round. Claims are accepted while
  `block.timestamp <= claimDeadline`.
- `sweep(roundId, to)` — owner only, after the deadline, moves that round's unclaimed remainder to
  `to` (CutPool, a treasury, or the distributor itself to recycle into the next round).
- `withdrawUnreserved(token, to, amount)` — owner only, limited to `balance - reserved[token]`
  (funds not assigned to any round, e.g. over-funding). Reserved funds are untouchable.
- Every state change emits an event (`RoundSet`, `Claimed`, `Swept`, `UnreservedWithdrawn`,
  `Received`, `OwnershipTransferStarted`, `OwnershipTransferred`).

**Leaf encoding (the off-chain tree must match this exactly):**

```
inner = keccak256(abi.encode(uint256 roundId, uint256 index, address account, uint256 amount))
      = keccak256( roundId‖index‖account‖amount )   four 32-byte big-endian words, address left-padded
leaf  = keccak256(bytes.concat(inner))               double hash (OpenZeppelin style)
node  = keccak256(min(a,b) ‖ max(a,b))               sorted pairs
```

Odd nodes are carried up unchanged (Uniswap merkle-distributor style), so their proofs have one
element fewer at that level. `roundId` is part of the leaf, so a proof from one round can never be
replayed in another. `MerkleDistributor.leaf(...)` is public so anyone can reproduce it.

## Trust model

| Action | Who | Notes |
|---|---|---|
| Change CutPool recipients / weights | **nobody** | immutable; redeploy to change |
| `distribute`, `distributeToken`, `unwrapWETH`, `claim` on CutPool | anyone | push-style; if a recipient rejects ETH the ETH split reverts |
| Call arbitrary functions from CutPool | **nobody** | only `claimTarget` × `claimSelector` |
| Publish a round (`setRound`) | distributor owner | once per id; must be pre-funded; cannot be edited afterwards |
| Claim a round entry | anyone | payout always goes to the leaf's `account` |
| Move unclaimed remainder (`sweep`) | distributor owner | only after `claimDeadline` |
| Withdraw funds not assigned to any round | distributor owner | never touches reserved round funds |

What the owner *can* still do wrong: publish a root that does not reflect real view counts, set a
short deadline, or never publish a round at all (funds then sit as "unreserved" and can be
withdrawn by the owner). Publishing `round_<n>.json` and the input `views.csv` every week lets
clippers verify the root themselves with `build_round.py`.

## Integration modes with Pons

Pons facts used here (from https://docs.ponsfamily.com/ and the public
[`ponsdotdev/ponsfamily`](https://github.com/ponsdotdev/ponsfamily) sources, 2026-09-06):
each V1 token trades in a Uniswap V3 pool against WETH (`0x0Bd7…AD73`) with a 1 % fee; on the
active factory (`0xA5aA…1feB`) 70 % of fees go to the creator and 30 % to the protocol; fees
accrue in the position held by the locker (`0x736D…7F35`); `launchToken` accepts a
`feeWallet`, the factory calls `locker.setFeeRedirect(token, feeWallet)`, and
`locker.feeRedirects(token)` tells you where creator fees are paid (zero → the deployer).

**Mode A — dev wallet is the creator (works today, requires trusting the dev).**
The dev launches CUT from their own wallet, claims creator fees from the Pons UI whenever they
like, and forwards the agreed share to CutPool (`cast send CUTPOOL --value …` or a WETH/CUT
transfer). From that point on everything is trustless: anyone can `distribute`. Deploy with
`CLAIM_TARGET`/`CLAIM_SELECTOR` empty.

**Mode B — CutPool is the creator / fee wallet (nobody has to trust anybody).**
Pass `feeWallet = CutPool` in `launchToken` (or, if the locker allows the creator to call
`setFeeRedirect` later, redirect an existing token). The locker then pays *all* creator fees to
CutPool, and anyone can trigger the claim with `CutPool.claim(calldata)` and split the proceeds
with `unwrapWETH`/`distribute`/`distributeToken`. Requirements before using mode B:
1. Read the locker's verified source on https://robinhoodchain.blockscout.com/address/0x736D76699C26D0d966744cAe304C000d471f7F35
   and find the function that pays out creator fees (name, arguments, who may call it).
2. Deploy CutPool with `CLAIM_TARGET = locker` and `CLAIM_SELECTOR = cast sig "<that signature>"`.
3. Confirm fees arrive as WETH (then `unwrapWETH(WETH)` → `distribute()`) or as ETH.
4. If the locker's claim can only be called by the fee wallet itself, that is exactly what
   `CutPool.claim` does (msg.sender = CutPool). If it is already permissionless, `claim` is just a
   convenience.

## Weekly round flow

1. Export views for every account that posted watermarked clips → `views.csv`
   (`address,handle,views`; duplicate addresses are merged, 0-view rows are excluded).
2. Bring this week's budget into the distributor: trigger the claim (mode B) or forward (mode A),
   then `unwrapWETH` + `distribute` / `distributeToken`. The distributor's share shows up as
   `available(token)`.
3. `python3 tooling/build_round.py --csv views.csv --total <available wei> --round <n> [--token 0x…]`
   → `round_<n>.json` with the root and every clipper's `{index, amount, proof}`.
   Amounts are `floor(total * views / sumViews)`; the last paid row absorbs the remainder so the
   sum is exactly `total`. The tool self-verifies every proof before writing.
4. `setRound(n, token, merkleRoot, total, claimDeadline)` from the owner wallet
   (`deploy.md` §7 has the exact `cast` lines; the tool prints one too).
5. Publish `round_<n>.json`; clippers (or a bot on their behalf) call `claim`.
6. After the deadline, `sweep(n, to)` recycles what was not claimed.

`--total` accepts `5e21`-style values. Add `pip install pycryptodome` for a faster keccak; without
it the script falls back to a bundled pure-Python keccak-256 (tested identical).

## Tests

```bash
forge install foundry-rs/forge-std@v1.9.7 --no-commit   # once
forge test -vv
```

Coverage (52 tests, all passing in this environment):

- **CutPool**: constructor validation; exact split math with 3 recipients incl. rounding dust
  (10 001 wei → 5000/3000/2001, thirds on 100 → 33/33/34, 1 wei → 0/0/1) plus a fuzz test that the
  shares always sum to the amount; ETH distribution with events; ERC-20 distribution for
  bool-returning and no-return (USDT-style) tokens and `false`-returning tokens; revert when a
  recipient rejects ETH; re-entrancy blocked; `claim` forwards calldata verbatim with zero value and
  `msg.sender == CutPool` to a mock locker, fees arrive and are splittable; `claim` reverts on zero
  target, on a foreign selector (`setFeeRedirect` attempt) and bubbles the target's revert reason;
  `unwrapWETH` with a WETH9-style `transfer`-based mock; rejection of a fake WETH; `receive()` works
  inside a 2 300-gas stipend.
- **MerkleDistributor**: leaf encoding; `setRound` funding/reservation accounting across rounds,
  bad-param and once-only checks, owner-only; claim happy path, anyone-can-submit, full drain,
  double-claim revert, six wrong-proof variants, cross-round replay revert, deadline (inclusive)
  and unknown-round reverts, understated-total protection, bitmap with indices 0/255/256/70000;
  sweep after deadline (and reverts before / non-owner / unknown / zero-to); ETH rounds incl. a
  claim to a rejecting account not being marked claimed; `withdrawUnreserved` limits; two-step
  ownership.
- **Python ↔ Solidity**: `test/fixtures/round_three.json` (3 leaves, exercises the odd-node carry)
  and `test/fixtures/round_example.json` (built from `tooling/views.example.csv`) are loaded with
  `vm.parseJson*`; the tests rebuild the tree in Solidity, assert the root and every proof are
  identical to the Python output, then set the round and execute every claim on-chain. A hardcoded
  copy of the 3-leaf root/proofs is asserted as well.

Also exercised manually on a local `anvil` chain: `script/Deploy.s.sol` (deploy both contracts),
send 1 ETH → `distribute()` → 0.5/0.3/0.2 split, `build_round.py` on the distributor's balance →
`setRound` → `claim` with a proof from the JSON → balances and `isClaimed` verified.

Toolchain used here: Foundry **1.7.1** (installed from the official npm packages
`@foundry-rs/forge|cast|anvil` because the installer domain was blocked), **solc 0.8.30** provided

## Design decisions (and deviations from the brief)

- `CutPool` constructor takes a 4th argument, `bytes4 claimSelector` (see rationale above).
  `claimTarget != 0` requires a non-zero selector and vice versa.
- Rounding dust goes to the last recipient (list the team or the distributor last).
- `MerkleDistributor.withdrawUnreserved` exists so mis-sent / over-sent funds are not stuck; it can
  never reach reserved round funds. Ownership transfer is two-step.
- Claims are inclusive of `claimDeadline`; `sweep` requires `block.timestamp > claimDeadline`.
- `claim` reverts with `AmountExceedsUnclaimed` if a published tree owes more than `total`, so a bad
  root can only under-pay its own round, never drain another round's reserve.
- No OpenZeppelin dependency: `SafeTransferLib` (≈20 lines) is vendored instead.
- `evm_version = "shanghai"` and `optimizer_runs = 1_000_000` (contracts are tiny; cheaper calls).

## Known unknowns / caveats

1. **Pons locker claim signature.** The locker at `0x736D76699C26D0d966744cAe304C000d471f7F35` is
   not in the public `ponsdotdev/ponsfamily` repo (only its `IPonsLaunchLocker` hooks
   `lockPosition`, `setFeeRedirect`, `protocolFeeRecipient` are, plus the documented views
   `feeRedirects(address)` and `tokenProtocolFeeShares(address)`). The docs say "the creator can
   claim at any time" and that "protocol automation may claim on behalf of creators", but the
   exact function, its arguments and its access control **must be read from the verified contract
   on Blockscout before mode B is used**. The explorer was not reachable from this environment.
2. Whether `setFeeRedirect` can be called by the creator after launch (vs. factory-only) is
   likewise unverified; passing `feeWallet` at launch is the documented path.
3. Whether creator fees are paid as WETH or unwrapped ETH is unverified; CutPool handles both.
4. Robinhood Chain ArbOS version / supported EVM version not verified — `shanghai` chosen as the
   conservative target.
5. The CUT token itself is created by Pons (fixed-supply `PonsLauncherToken`); it is not part of
   this repo.
6. `distribute()` is push-based: a recipient contract that cannot receive ETH bricks ETH splits
   (tokens are unaffected). Use EOAs or contracts with a `receive()` (MerkleDistributor has one).
7. No audit. Contracts are small and fully tested, but treat them as unaudited code.
